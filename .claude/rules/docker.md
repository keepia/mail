# Docker
- **Pins** (`tools/check-image-pins`, `make image-pins`): `# syntax=` is `name:X.Y.Z@sha256:<64 hex>`; every `FROM`, `COPY --from=` and `RUN --mount=…,from=` is an earlier stage or `name:tag@sha256:<64 hex>`; Compose's upstream images are `tag@sha256`; own images are built from local contexts; workflow `container`/`services` images are pinned by digest. Write every `--flag` on the instruction's first line, ADD sources literally (no `$VAR`), no here-documents, no `ONBUILD`, no bake `contexts`. The bake rule reads `docker buildx bake --print`, so `make image-pins` needs Docker with buildx.
- **The check is part of every build:**
  - Locally, images are built only by `go run ./tools/check-image-pins -bake-local` (`make images`). It resolves, checks and then builds with one argument list, a cleaned environment and one docker binary (its absolute path, looked up once), and takes only typed options (`-ca`, `-host-network`, `-https-proxy`, `-version`, `-registry`, `-platform`).
  - A Makefile or `*.mk` file names no `buildx`, no `BUILDX_` and no other build command, sets or exports no `PATH` or `HOME`, and names no `DOCKER_CONFIG`, `DOCKER_HOST` or `DOCKER_CONTEXT`.
  - In CI, a job builds only through one `docker/bake-action` step (`id: build`, inputs from the job env `BAKE_TARGET`/`BAKE_SET`/`PLATFORM`, with expressions reading only `matrix.*` and `github.event_name`; no `sbom` or `provenance` input).
  - `BAKE_SET` sets only a `type=gha` cache in the row's own scope. No step of the job writes `GITHUB_ENV` or `GITHUB_PATH`, except `SOURCE_DATE_EPOCH` and `scripts/ci-docker-mirror.sh`'s `DOCKER_CONFIG`.
  - The step right before the build is exactly `GOENV=off GOFLAGS= GOWORK=off go run ./tools/check-image-pins -build "$BAKE_TARGET" -build-set "$BAKE_SET"`. The step right before any step that runs `image-test` or `docker save`/`push`/`tag` (also in a script it names or a local action it uses) is `GOENV=off GOFLAGS= GOWORK=off go run ./tools/check-image-pins -verify-built` with `BAKE_METADATA: ${{ steps.build.outputs.metadata }}`.
  - Nothing after verify goes by tag: a test runs the verified ID (`VERIFIED_IMAGE: ${{ steps.<verify id>.outputs.image }}`), and the image is saved only by `-verify-built -save "$RUNNER_TEMP/<name>.tar"`, which checks the tar it wrote.
  - No other build path: no `docker`/`podman`/`nerdctl` build, `buildx build`/`bake`, Compose build (`compose build`, `up --build`, `docker-compose`), build action, remote reusable workflow or building composite action or script, in any language. The only bake files are the root's `docker-bake.hcl` and `docker-bake.override.hcl`.
  - A new bake variable needs a sentinel in `tools/check-image-pins/bake.go` if the generic one does not resolve.
- **Threat model:**
  - The check catches accidental unpinned references and fails closed on forms it cannot resolve.
  - Local, build and verify mode are authoritative, because they check what is actually built.
  - Verify proves the image store's state only while it runs. So the test runs the verified image ID and the save checks the tar it wrote: a re-tag after verify, also inside the same step, cannot change what is tested or saved.
  - The tool's own build inputs are fixed in CI (`GOENV=off GOFLAGS= GOWORK=off`, no other `GITHUB_ENV`/`GITHUB_PATH` write in a build job), and in local mode the docker binary is resolved once and the Makefile may not set what local mode passes to docker.
  - Repository mode is best effort for value-conditional HCL expressions. Its known limits are single-value sentinels and `timestamp()` conditions.
  - The build-path rules are a word-level heuristic (defence in depth). They catch the accidental forms: global options before a subcommand, Compose and nerdctl builds, and list syntax in other languages.
  - A change that edits the check, or disables or routes around it, is caught by review, not by the tool. Examples: a build command assembled at run time, a computed variable name, a background process that changes the image store after verify, or a tar changed between save and upload. Reviewers of `second-review` PRs check that every build still goes through the paths above.
- Compose `build` keys only `context`, `dockerfile`, `args` (no `BUILDKIT_SYNTAX`), `target` and `labels`.
- **Downloads only by `ADD --checksum=sha256:`**, one URL per `ADD`, from a source the plan lists. No `curl`, `wget`, `pip install` from an index, `git clone` or any other download in `RUN`: the check cannot see them, so review must. Debian packages come from the Debian archive through `images/common/keepia-apt-install`, which records them in `/usr/share/keepia/packages.txt` (recorded, not pinned).
- A new registry, base image, package source or action is a new external service: the maintainer's OK first.
- **Privileges:** `cap_drop: [ALL]`, `no-new-privileges`, and exactly the capabilities the plan lists per container (Postfix: `CHOWN DAC_OVERRIDE FOWNER SETUID SETGID`, with `chroot = n` for every `master.cf` service; Dovecot: `SYS_CHROOT`; all others none). Fixed non-zero uids; only Postfix's master runs as root. No `privileged`, host network or Docker socket.
- **R-BIND-PRIVATE:** every listener binds the container's fixed private address or loopback, never `0.0.0.0` or `::`.
- **Healthchecks need a protocol reply** (an SMTP `220 `, `unbound-control status`, `/healthz`), never only a process or an open port, and each is measured red with the service broken or stopped (`scripts/image-test.sh`).
- Reloads: Postfix and Unbound reload through `images/common/keepia-reload-watch` (architecture section 5); keep its tests in `scripts/image-test.sh` green.
- Changes here are container privileges or networking: `second-review`.
