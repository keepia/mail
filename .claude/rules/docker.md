# Docker
- **Pins** (`tools/check-image-pins`, `make image-pins`): `# syntax=` is `name:X.Y.Z@sha256:<64 hex>`; every `FROM`, `COPY --from=` and `RUN --mount=…,from=` is an earlier stage or `name:tag@sha256:<64 hex>`; Compose's upstream images are `tag@sha256`; own images are built from local contexts; workflow `container`/`services` images are pinned by digest. Write every `--flag` on the instruction's first line, ADD sources literally (no `$VAR`), no here-documents, no `ONBUILD`, no bake `contexts`. The bake rule reads `docker buildx bake --print`, so `make image-pins` needs Docker with buildx.
- **The check is part of every build:**
  - Locally, images are built only by `go run ./tools/check-image-pins -bake-local` (`make images`). It resolves, checks and then builds with one argument list, a cleaned environment and one docker binary (its absolute path, looked up once), and takes only typed options (`-ca`, `-host-network`, `-https-proxy`, `-version`, `-registry`, `-platform`).
  - A Makefile or `*.mk` file names no `buildx`, no `BUILDX_` and no other build command, sets or exports no `PATH` or `HOME`, and names no `DOCKER_CONFIG`, `DOCKER_HOST` or `DOCKER_CONTEXT`. It also sets no `SHELL` or `.SHELLFLAGS`, sets or exports no `GOFLAGS`, `GOENV` or `GOWORK`, sets `GO` only to `go`, includes only literal `*.mk` files the check reads, and computes no variable name (`PA$(E)TH`).
  - In CI, a job builds only through one `docker/bake-action` step (`id: build`, inputs from the job env `BAKE_TARGET`/`BAKE_SET`/`PLATFORM`, with expressions reading only `matrix.*` and `github.event_name`; no `sbom` or `provenance` input).
  - `BAKE_SET` sets only a `type=gha` cache in the row's own scope. No step of the job writes `GITHUB_ENV` or `GITHUB_PATH` (also `core.exportVariable`/`core.addPath` in `actions/github-script`), except `SOURCE_DATE_EPOCH` and `scripts/ci-docker-mirror.sh`'s `DOCKER_CONFIG`.
  - Every step of a job that builds runs only what the check can read: scripts by their repository path (also as `$GITHUB_WORKSPACE/…`, `${{ github.workspace }}/…`, under `working-directory:` or `cd`, or `$(dirname "$0")/…` inside a script, `$GITHUB_ACTION_PATH/…` in an action; a relative path is followed in every directory it may run in), `make <target>` with an explicit rule, and local actions (also nested). Running `make` reads the whole Makefile and its literal includes as well. A script path the check cannot resolve, a command word that is a variable (`"$SAVE"`, `sh -c "$CMD"`; a variable the script sets only to plain command names, such as `SUDO=sudo`, is replaced by its value and the command read again; `"$@"`/`"$N"` as a command is skipped only inside a function body; at a script's top level it forwards the caller's arguments as a command and is reported: call the command directly; so is a top-level call that passes its arguments (`"$@"`, `"$*"`, `"$N"`, also with any operator such as `${1+"$@"}` or `"${1?msg}"`), or any other variable or command substitution (`"${args[@]}"`, `$cmd`), to a function whose body runs its positional parameters as a command word, also in a loop, after `shift`, or through a nested or further function, as in `main() { for i in 1 2 3; do "$@" && return 0; done; }; main "$@"`, and also when a body passes on a copy (`local args=("$@"); retry "${args[@]}"`, `local c="$*"; run $c`, `read -r -a a <<< "$*"`), but not a plain data variable such as `"$c"` with `c=$1` (#67)), a Makefile construct the check does not model (conditionals, `define`, `.DEFAULT_GOAL`, `$(eval)`/`$(call)`) or a prerequisite with neither rule nor file, or more than 200 files, is reported.
  - The step right before the build is exactly `GOENV=off GOFLAGS=-mod=readonly GOWORK=off go run ./tools/check-image-pins -build "$BAKE_TARGET" -build-set "$BAKE_SET"`. The step right before any step that runs `image-test` or `docker save`/`push`/`tag`, Compose push, `buildx imagetools create`, crane or skopeo (also in a script, make target or local action it runs) is `GOENV=off GOFLAGS=-mod=readonly GOWORK=off go run ./tools/check-image-pins -verify-built` with `BAKE_METADATA: ${{ steps.build.outputs.metadata }}`.
  - Nothing after verify goes by tag: a test runs `scripts/image-test.sh <name> "$VERIFIED_IMAGE"` (`VERIFIED_IMAGE: ${{ steps.<verify id>.outputs.image }}`; `make image-test` tests a tag), the image is saved only by `-verify-built -save "$RUNNER_TEMP/<name>.tar"`, which checks the tar it wrote, and pushed only as `docker tag "$VERIFIED_IMAGE" <name>` and `docker push <name>` in one step. Compose push, `buildx imagetools create`, crane and skopeo are not used after the build.
  - No other build path: no `docker`/`podman`/`nerdctl` build, `buildx build`/`bake`, Compose build (`compose build`, `--build`, `up`/`create` without `--no-build`, and every `compose run`, which has no `--no-build`: use `up -d --no-build` and `exec`; also `docker-compose`), build action, remote reusable workflow or building composite action, github-script or script, in any language. The only bake files are the root's `docker-bake.hcl` and `docker-bake.override.hcl`.
  - A new bake variable needs a sentinel in `tools/check-image-pins/bake.go` if the generic one does not resolve.
  - **Release surface (rule 7, #27):** only `.github/workflows/release.yml` (that exact path) may grant `packages: write`, and it has exactly the policy in `tools/check-image-pins/release.go`: the ten jobs with their permissions, `needs` and `if`; in `push`, `push-rehearsal`, `index`, `latest`, `attest`, `attest-assets` and `release` exactly the policy's steps, actions at the policy's pinned commit (`actionPins`; a Dependabot bump of `release.yml` bumps it in the same PR) with exact inputs (setup-go with `cache: false`, in every job; setup-buildx with the pinned BuildKit image, in every job and in every workflow) and run steps that equal one fixed line (nothing resolved: no script, make target, other `go run`, function, `eval`, `sh -c`, `source` or `xargs`); every `env` a literal mapping, never an expression; the release modes (in any spelling) and `docker login` (also inside `sh -c`) only in the exact jobs; action names compared without case; no `actions/cache`, `docker://` step or `anchore/` action, and no container run other than the build row's package-list line; the workflow-level `concurrency: {group: release, cancel-in-progress: false}`; `on: workflow_dispatch` only. The push jobs push only through the bake step by digest (`BAKE_SET` exactly the release cache, the bare repository as tags, the two outputs with `push=true` and `attest=type=provenance,mode=max`, checked again in build mode with the tags and `VERSION`), then `-verify-pushed` compares the pushed config with the tested one and reads the row back from the registry; tags are written only by `-publish-index` (`X.Y.Z`, immutable) and `-move-latest` (`latest`, forward only, after the highest-tag guard). The bare tags (BuildKit refuses push-by-digest of a tagged name, #75) are safe only with `push-by-digest=true`: without it BuildKit pushes them as `:latest`, so rule 7 and build mode both require it. `push-rehearsal` pushes to its own pinned `registry` service on `127.0.0.1:5000` with a `network=host` builder; no other job has `services` or `network=host`. A change to the release policy is a change to the check: `second-review`.
- **Threat model:**
  - The check catches accidental unpinned references and fails closed on forms it cannot resolve. In a job that builds, that includes the scripts a step runs: a path it cannot resolve to a file in the repository is reported, not skipped. It does not model every shell form; it reports what it cannot read.
  - Local, build and verify mode are authoritative, because they check what is actually built.
  - Verify proves the image store's state only while it runs. So the test runs the verified image ID and the save checks the tar it wrote: a re-tag after verify, also inside the same step, cannot change what is tested or saved. A push tags the verified ID and pushes that name in the same step; a re-tag between the two commands is deliberate and for review.
  - The saved tar is checked as both image stores load it: one `manifest.json` and one `index.json` entry per name, naming the same config, with the config's layers. This guards against a malformed save; a tar changed on purpose after the check is for review.
  - The tool's own build inputs are fixed in CI (`GOENV=off GOFLAGS=-mod=readonly GOWORK=off`: no go env file, no `go.work`, no `vendor/`; no other `GITHUB_ENV`/`GITHUB_PATH` write in a build job), and in local mode the docker binary is resolved once and the Makefile may not set what local mode passes to docker or what `go run` builds the tool with.
  - Repository mode is best effort for value-conditional HCL expressions. Its known limits are single-value sentinels and `timestamp()` conditions.
  - The build-path rules are a word-level heuristic (defence in depth). They catch the accidental forms: global options before a subcommand, Compose and nerdctl builds, list syntax in other languages (also split over lines), and github-script.
  - In `release.yml`'s jobs with `packages: write`, rule 7 refuses every text that is not one of its fixed lines, so the limits below do not apply there. A dispatch on a branch runs that branch's `release.yml`: a residual risk for review.
  - Known limits of following what a step runs (#51): literal words given to a function that runs its arguments (`retry make publish` with `retry() { "$@"; }`) are read only as words of the text; a function is known only in the text that defines it and its inline commands (`eval`, `sh -c`), not in a file that sources it (`. lib.sh; run "$@"`); a shell that reads its program from stdin (`bash <<< "$*"`) is not read; `xargs` and other words on PATH that run their arguments (`xargs make publish`, `stdbuf`) hide them; a top-level copy of the arguments used in a function called with no arguments (`args=("$@"); run() { main "${args[@]}"; }; run`) is not followed; reading `make` takes in the whole Makefile, which over-reports.
  - A change that edits the check, or disables or routes around it, is caught by review, not by the tool. Examples: a build command assembled at run time, a background process that changes the image store after verify, or a tar changed between save and upload. Reviewers of `second-review` PRs check that every build still goes through the paths above.
- Compose `build` keys only `context`, `dockerfile`, `args` (no `BUILDKIT_SYNTAX`), `target` and `labels`.
- **Compose template** (`docker-compose.yml`): an own image is `${KEEPIA_<NAME>_IMAGE:-${KEEPIA_REGISTRY:-ghcr.io/keepia}/mail-<name>:${KEEPIA_VERSION:-dev}}` (`KEEPIA_IMAGE` for Keepia), never pinned by digest (km would pull it). Rule 4 checks that whole name, not only its prefix: the default is exactly `ghcr.io/keepia` and the name `mail` or `mail-<name>` (#61). The CI `compose` job loads the `docker-build` tars, runs `-verify-built` on each with its build's `metadata.json`, and sets these variables to the verified IDs, so no tag is used between the load and Compose. Start it only with `up -d --no-build --pull never`; no `:?` required variables (`docker buildx bake` reads this file too and would fail). Every listener on the container's fixed address or loopback; `scripts/compose-test.sh` checks it per listener (tests 6, 8–14).
  - **Docker Engine 28 or later:** every internal network has `com.docker.network.bridge.gateway_mode_ipv4/ipv6: isolated`, so its bridge has no host address: host processes cannot reach the unauthenticated services (memcached, olefy, clamd, rspamd) and containers cannot reach host services through the bridge (#61; test 9). `edge-public` keeps the default `nat`. Engine 27 refuses to create the networks; 26 and older create them without the isolation, silently, and `docker network inspect` still shows `isolated` (architecture section 7 has the operator's check, meaningful after the first start: the host must have no address in the internal subnets; `edge-public`, which is not internal, keeps its gateway address on the host).
  - **Edge addresses:** `deploy/edge/check-edge-addresses.sh` refuses a wildcard `EDGE_IPV4`/`EDGE_IPV6`, in two places (#61; test 14):
    - on `up`: the one-shot `edge-addresses` (the pinned Dovecot image, no network) runs it, and `edge-postfix` depends on it (`service_completed_successfully`), so a refused `up` publishes nothing. It leaves `edge-postfix` Created with the wildcard in its port bindings;
    - on any start of `edge-postfix`: its entrypoint runs the check before the image's own (`tini -- sh check-edge-addresses.sh keepia-reload-watch`), so a start that skips the dependency (`restart`, `docker start`, `up --no-deps`) exits 1 before Postfix runs. Docker publishes the port for that moment and, under `restart: unless-stopped`, for each retry: docker-proxy can briefly accept a TCP handshake, but nothing in the container listens and no data is handled (Review B on PR #65: 8 of 6468 probes accepted, no `220` banner).
    - Recovery after a refusal: fix `.env`, then `docker compose rm -f edge-postfix` and `up` again (or `up --force-recreate`).
    - km does not start the edge role, so the check is not in km.
  - **Every service has `pids_limit`**, well above its use (`compose-test.sh` lists use and limit). Revisit store-dovecot's 256 before IMAP is exposed: imap, imap-login, lmtp and auth may each run up to `default_process_limit` (100) (Review B N4 on PR #65).
- **Downloads only by `ADD --checksum=sha256:`**, one URL per `ADD`, from a source the plan lists. No `curl`, `wget`, `pip install` from an index, `git clone` or any other download in `RUN`: the check cannot see them, so review must. Debian packages come from the Debian archive through `images/common/keepia-apt-install`, which records them in `/usr/share/keepia/packages.txt` (recorded, not pinned).
- A new registry, base image, package source or action is a new external service: the maintainer's OK first.
- **Privileges:** `cap_drop: [ALL]`, `no-new-privileges`, and exactly the capabilities the plan lists per container (Postfix: `CHOWN DAC_OVERRIDE FOWNER SETUID SETGID`, with `chroot = n` for every `master.cf` service; Dovecot: `SYS_CHROOT`; all others none). Fixed non-zero uids; only Postfix's master runs as root. No `privileged`, host network or Docker socket.
- **R-BIND-PRIVATE:** every listener binds the container's fixed private address or loopback, never `0.0.0.0` or `::`. A new listener adds its protocol, address and port (`tcp:<network>:<port>`) to `want_listen` in `scripts/compose-test.sh`.
- **Healthchecks need a protocol reply** (an SMTP `220 `, `unbound-control status`, `/healthz`), never only a process or an open port, and each is measured red with the service broken or stopped (`scripts/image-test.sh`).
- Reloads: Postfix and Unbound reload through `images/common/keepia-reload-watch` (architecture section 5); keep its tests in `scripts/image-test.sh` green.
- Changes here are container privileges or networking: `second-review`.
